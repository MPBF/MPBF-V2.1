# تصميم تعدد اللغات لواجهة MPBF Next

## الهدف

دعم العربية والإنجليزية في واجهة التطبيق مع الحفاظ على تجربة العربية الحالية كافتراضية، وضمان أن تتغير لغة النصوص واتجاه الصفحة معًا. ينبغي أن يكون نقل النصوص تدريجيًا وقابلًا للاختبار، وألا يغير قيم التصنيع أو البيانات التي يدخلها المستخدم.

## الوضع الحالي

- نصوص عربية كثيرة مكتوبة مباشرة في `client/src/App.tsx` والصفحات والمكونات، ولا تستخدم مفاتيح ترجمة.
- `i18next` و`react-i18next` موجودتان ضمن الاعتماديات، لكن لا توجد تهيئة أو استخدام فعلي لهما.
- `company_profile.default_language` موجود، لكن تغييره لا يبدل لغة التطبيق.
- `/api/me` يعيد المستخدم الحالي، ولا يوجد حقل لتفضيل اللغة الشخصي.
- مستند HTML واتجاه عدد من الصفحات والتقارير ثابت على العربية وRTL.
- توجد ملاحظة في `.agents/memory/i18n-duplicate-keys.md` تشير إلى ملفات ترجمة قديمة تحت `client/src/i18n/locales/`، لكن الملفات غير موجودة في نسخة العمل الحالية حتى عند تضمين الملفات المستثناة من البحث. يجب التحقق من تاريخ المستودع عند الحاجة، وعدم افتراض وجود موارد قابلة لإعادة الاستخدام.

## القرار المعماري

1. استخدام `i18next` و`react-i18next` الموجودتين، مع موارد ترجمة TypeScript أو JSON منظمة حسب المجال، مثل `common` و`orders` و`admin` و`hr`.
2. إضافة عمود اختياري `preferred_language` إلى `users`، يقبل `ar` أو `en` أو `NULL`. عند غيابه، تستخدم الواجهة `company_profile.default_language`، ثم `ar` كقيمة احتياطية نهائية.
3. تحديث `AuthenticatedUser` و`resolveUser` في `server/auth.ts` كي يشملا التفضيل، ثم إرجاعه عبر `/api/me`. إضافة مسار مصادق عليه لتحديث تفضيل المستخدم الحالي فقط مع تحقق Zod لقيم `ar` و`en`؛ لا يسمح للمستخدم بتحديث تفضيل مستخدم آخر.
4. تحديث `document.documentElement.lang` و`dir` عند التبديل: `ar` مع `rtl` و`en` مع `ltr`. استخدام CSS logical properties حيث تؤثر قواعد الاتجاه على التخطيط.
5. مفاتيح الترجمة تمثل نصوص الواجهة، ولا تستبدل رموز المجال المخزنة مثل `pending` أو أسماء العملاء والمنتجات. تُعرض الرموز عبر خرائط ترجمة، وتبقى قيم المستخدم كما أُدخلت.
6. رسائل أخطاء API المعروفة تستخدم خرائط الترجمة في الواجهة. عند تلقي رسالة عربية غير معروفة في الواجهة الإنجليزية، يظهر fallback إنجليزي مفهوم بدل تسريب نص عربي أو مفتاح ترجمة خام؛ يمكن نقل المسارات لاحقًا إلى رموز أخطاء مستقرة.
7. تنسيق التاريخ والأرقام يبقى عبر `Intl` ويعتمد اللغة المختارة مع إبقاء المنطقة الزمنية إعدادًا مستقلًا.

## خطة التنفيذ المرحلية

### المرحلة الأولى: البنية والتفضيل

- تهيئة i18next وموارد العربية والإنجليزية، وفحص المفاتيح المفقودة أثناء التطوير.
- إنشاء نقطة تهيئة i18next وموارد ترجمة فعلية لكل لغة، وتوصيل React بـ `I18nextProvider` أو نمط التهيئة المعتمد من المكتبة.
- إضافة `preferred_language` إلى مخطط Drizzle وترحيل SQL إضافي قابل لإعادة التطبيق، بقيمة nullable حتى تستمر الحسابات الحالية في استخدام لغة الشركة الافتراضية.
- تحديث نوع المستخدم المحمّل من قاعدة البيانات و`resolveUser` وبيانات `/api/me`، وإضافة مسار تحديث ذاتي مصادق عليه مع تحقق صارم للغة.
- إضافة مبدّل لغة إلى غلاف التطبيق وربطه بالحفظ، وتحديث سمات HTML والاتجاه عند بدء الجلسة وعند التبديل.
- إضافة مبدّل مؤقت في شاشة الدخول وتغيير كلمة المرور كي يمكن اختيار اللغة قبل المصادقة؛ لا يحفظ هذا المبدّل تفضيلًا شخصيًا قبل تسجيل الدخول.
- نقل التنقل والعناصر المشتركة ورسائل التحميل والأخطاء العامة إلى مفاتيح ترجمة لاختبار المسار من طرف إلى طرف.
- الحفاظ على توافق أخطاء API الحالية التي ترسل `message` أثناء الانتقال؛ إضافة `code` ثابت للأخطاء المنقولة، وترجمة هذا الرمز في الواجهة بدل عرض رسالة بلغة مختلفة عن لغة الواجهة. تكون الرسالة العامة المترجمة هي الاحتياط عند غياب رمز أو ترجمة.

### المرحلة الثانية: نقل شاشات الأعمال

- نقل الصفحات والمكونات حسب المجال إلى ملفات الترجمة، مع الحفاظ على مفاتيح واضحة وعدم تكرار النصوص المشتركة.
- ترتيب التنفيذ حسب المسارات الشائعة: الطلبات والإنتاج، الإدارة، الموارد البشرية، ثم بقية النماذج والقوائم.
- تضمين الحوارات، حالات الفراغ، التنبيهات، تأكيدات المتصفح، عناوين الوصول، والطباعة والتقارير المنبثقة.
- إزالة النصوص الثابتة من الواجهة المستهدفة فقط بعد اكتمال ترجمتَي العربية والإنجليزية لكل شريحة.

### المرحلة الثالثة: التحقق والتشديد

- اختبار اختيار اللغة وحفظها واستعادتها، وتفضيل المستخدم على لغة الشركة، ثم الاحتياط للعربية.
- اختبار اتجاه RTL/LTR في الشاشات والنوافذ والطباعة والتقارير، والتحقق من عدم انقلاب ترتيب الأرقام والمعرفات.
- إضافة فحص آلي يمنع مفاتيح ترجمة مفقودة أو مفاتيح غير مستخدمة، وإرشادات lint تدريجية تمنع إضافة نصوص واجهة ثابتة جديدة.
- فحص الشاشات الرئيسية بالعربية والإنجليزية على أحجام عرض مكتبية وهاتفية قبل اعتبار النقل مكتملًا.

## التوافق والسلامة

- تظل قيمة `default_language` الحالية فعالة للمستخدمين الذين لم يحددوا تفضيلًا شخصيًا.
- الترحيل إضافي فقط، ولا يعدل بيانات المستخدمين الحالية أو بيانات المصنع.
- تتطلب العمليات متعددة الجداول، إن وجدت، معاملات وفق نمط المشروع؛ ولا تُضاف أي تغييرات على قواعد الإنتاج أو الصلاحيات.
- لا تعتبر الواجهة متعددة اللغات مكتملة حتى تُنقل كل النصوص المرئية ورسائل الأخطاء والتقارير في النطاق، وتنجح اختبارات اللغتين والاتجاه.

## التحقق ومعايير القبول

- مستخدم بلا تفضيل يرى لغة الشركة، وإن لم تكن محددة يرى العربية.
- يستطيع المستخدم تبديل لغته، وتبقى اللغة المختارة بعد تسجيل الخروج والدخول.
- تُرفض قيم اللغة غير المدعومة، ولا يستطيع المستخدم تعديل تفضيل مستخدم آخر؛ يظل الحقل غائبًا/فارغًا للمستخدمين الحاليين حتى يختاروا لغة.
- يغير التبديل النصوص المرئية و`lang` و`dir` معًا، ولا يغير القيم المخزنة أو سلوك التصنيع.
- تظهر النصوص العربية والإنجليزية الصحيحة في الصفحات المشتركة والصفحات المنقولة، ولا تظهر مفاتيح خام أو نصوص مبتورة.
- تنجح فحوص TypeScript والاختبارات الحالية واختبارات تفضيل اللغة والترجمة والاتجاه.

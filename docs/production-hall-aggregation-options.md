# مقارنة كلفة فتح صالة الإنتاج وخطة التحسين المقترحة

## القرار المطلوب وحدود العمل

**اعتماد نطاق الإغلاق:** اختار المستخدم «اعتماد الدراسة والخطة فقط وإغلاق
هذه المرحلة». لذلك تُغلق هذه المرحلة بوصفها دراسة مقارنة وخطة تحسين، لا
بوصفها إصلاحاً مطبقاً يثبت زمن فتح الصالة. هذا الاعتماد لا يأذن ببدء نموذج
التجميع أو تجربة الفهارس أو تعديل قاعدة التطبيق أو القاعدة المنشورة أو النشر.
أي متابعة تنفيذية تحتاج موافقة جديدة.

هذه **نتيجة دراسة محلية وخطة للموافقة، وليست تحسيناً مطبقاً على التطبيق**.
لم تتغير استعلامات `server/production/read.ts` أو
`server/production/read-queries.ts`، ولم يُضف فهرس أو جدول تجميعي جديد، حتى
في تجربة المقارنة. لم تتصل التجربة بقاعدة التطبيق أو القاعدة المنشورة،
ولم تُنفذ هجرة أو عملية نشر.

**التوصية:** لا نعتمد زيادة الذاكرة أو إعادة صياغة التجميع وحدهما حلاً لنمو
الأرشيف. البديل الأسرع محلياً خفض وسيط فتح الصالة بنحو **15.8%**، لكنه ما
زال يقرأ الأرشيف ويجري أكثر من مئة ألف بحث في فهرس الاستلام. نوصي بالموافقة
أولاً على تجربة محلية إضافية للفهرسة، ثم نموذج تجميع دقيق يُحدَّث مع كل
معاملة إذا كان المطلوب إزالة مسح الأرشيف من مسار القراءة. اعتماد أي منهما
في التطبيق أو القاعدة المنشورة يحتاج موافقة مستقلة بعد قياسه والتحقق منه.

المرجع السابق: [قياسات تاريخ الإنتاج](production-history-performance.md)،
خصوصاً نتائج `scripts/production-read-plans.ts`. البحث في صفحات التاريخ
ليس موضوع هذه الدراسة ولا بديلاً عن قائمة العمل الحالية.

## المنهج والعزل

- PostgreSQL **16.10** محلي، loopback، قاعدة مؤقتة باسم
  `factory_isolated_test` على المنفذ `55439` ومخطط عشوائي مخصص للاختبار.
  تُحذف القاعدة مع العنقود المؤقت بعد انتهاء كل تشغيل.
- تشغيلان مستقلان: **10,000** و**100,000** أمر أرشيف صناعي؛ لكل أمر ثلاثة
  رولات وسند استلام، إضافة إلى حالات دورة الإنتاج الأصلية.
- في كل حجم بقيت **70** أوامر أرشيف قديمة ذات رصيد غير مستلم، خارج أول صفحة
  تاريخ. اختُبرت حالة **121** رولاً وأكثر من **60** استلاماً لأمر واحد:
  جاهز **22.00 kg**، مستلم **15.00 kg**، متبقٍ **7.00 kg**.
- استُدعيت خدمة `ProductionReadService.state()` الحقيقية للإدارة والصالة،
  مع الصلاحيات نفسها وتعطيل أخذ عينات سجل الأداء في المقارنة فقط.
  يلتقط الغلاف SQL الفعلي ويغيّر بادئة اختيار الأوامر فقط، ويترك
  `selected` و`orderSelect` وبقية استعلامات الحالة كما هي.
  يتوقف صراحة إذا تغيّر شكل SQL بدلاً من قياس صيغة قديمة بصمت.
- لكل بديل ولكل شاشة: إحماء واحد ثم **خمس عينات**، مع تدوير ترتيب البدائل.
  الوسيط يشمل تنفيذ الخدمة ونقل البيانات وتسلسل JSON، وليس زمن المتصفح أو
  الشبكة. فحص تطابق الكائن الكامل يقع خارج توقيت العينة.
- جميع القراءات داخل `REPEATABLE READ READ ONLY` مع مهلة محلية **30s**.
  يتحقق الغلاف من العزل فعلياً؛ كلفة إعداد الجلسة والتحقق منه موجودة بالتساوي
  في البدائل، وليست جزءاً من التطبيق.
- بعد العينات، نُفذ `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` مرة لكل بديل
  ولكل شاشة. أزمنته منفصلة، ولا تُخلط مع وسيط الخدمة. لا تُطبع SQL أو
  المعاملات أو محتويات المنتجات في تشخيص المقارنة.
- الأرقام محلية بذاكرة دافئة، وليست اتفاقية أداء للإنتاج. البيانات الصناعية
  متجانسة ومعظم الأرشيف جاهز ومستلم بالكامل؛ لا تمثل جميع توزيعات عدد
  الرولات/الاستلامات أو تنافس الاتصالات. لا يجوز مقارنة هذه الأزمنة مباشرة
  بالتشغيل السابق في الوثيقة المرجعية.

## البدائل المقاسة

| المعرّف | الاختلاف عن الاستعلام الحالي | تغيير دائم |
| --- | --- | --- |
| `baseline` | الاستعلام الفعلي الحالي بدون تعديل | لا |
| `aggregate_first` | تجميع الوزن الإجمالي والصافي للرولات المنتهية قبل ربط التنفيذ، مع تجميع الاستلام الكامل كما هو | لا |
| `lateral_receipts` | التجميع السابق مع حساب الاستلام لكل أمر جاهز عبر `LATERAL` والفهرس الموجود، بدلاً من تجميع سندات الأرشيف كلها مرة واحدة | لا |
| `memory_64mb` | SQL الحالي نفسه مع `SET LOCAL work_mem='64MB'` بدلاً من الافتراضي `4MB` | لا؛ داخل معاملة الاختبار فقط |

جميع البدائل تحتفظ بمعادلة الجاهز: وزن الرول لمنتج الرولات، والوزن الصافي
للأكياس، وللرولات في مرحلة `done` فقط. لم نضف شرط تاريخ أو حالة اكتمال
التصنيع إلى الاستلام، ولم نقسم قائمة العمل إلى صفحات.

## ماذا تكشف خطط التنفيذ؟

عند 100 ألف أمر، قياس واحد بـ `EXPLAIN ANALYZE` لاستعلام اختيار الأوامر
وإسقاط بياناتها، لا للخدمة كاملة:

| الشاشة | البديل | التنفيذ ms | shared hit blocks عند الجذر | temp blocks مكتوبة عند الجذر |
| --- | --- | ---: | ---: | ---: |
| الإدارة | الحالي | 764.878 | 319,758 | 3,709 |
| الإدارة | التجميع قبل الربط | 868.398 | 319,284 | 4,004 |
| الإدارة | الاستلام لكل أمر | 610.636 | 616,685 | 782 |
| الإدارة | ذاكرة 64 MB | 913.460 | 22,128 | 0 |
| الصالة | الحالي | 716.833 | 313,454 | 3,708 |
| الصالة | التجميع قبل الربط | 767.192 | 313,179 | 4,002 |
| الصالة | الاستلام لكل أمر | 526.866 | 610,580 | 782 |
| الصالة | ذاكرة 64 MB | 652.922 | 15,885 | 0 |

هذه عدادات الجذر؛ **لا تُجمع عدادات الأبناء معها** كي لا تُحتسب الكتل مرتين.
كل خطط المقارنة هنا سجلت صفراً من `shared_read_blocks` عند الجذر.
`shared_hit_blocks` عدد زيارات إلى الكتل وليس عدد صفحات فريدة.

- الحالي يجمع **300,144** رولاً منتهياً و**100,067** بند استلام، ويربط
  التنفيذ من الأرشيف قبل إرجاع عشرات الأوامر فقط. كلفة اختيار الأوامر أكبر
  من كلفة إسقاط تفاصيل المجموعة الصغيرة، لكن كليهما محفوظ في القياس.
- إعادة ترتيب التجميع لم تقلل المصدر المقروء وزادت الكتابة المؤقتة.
- `lateral_receipts` خفض الكتابة المؤقتة، لكنه بحث في فهرس الاستلام
  **100,013 مرة**؛ نحو **300,033** زيارة كتلة لهذا الجزء وحده.
  لا تعني كلمة «لكل أمر» هنا «لكل أمر ظاهر»؛ فحص الرصيد يسبق معرفة الأوامر
  التي ستظهر. لذلك يبقى نمو الأرشيف مؤثراً.
- رفع `work_mem` أزال الكتابة المؤقتة في هذه العينة، لكنه لم يحسن زمن الخدمة
  عند الحجم الكبير. الذاكرة تُستهلك لكل عقدة تنفيذ/عامل ولكل اتصال متزامن،
  وليست 64 MB واحدة لكل التطبيق؛ لا نوصي بتغيير عام أو تلقائي.
- `orderSelect` في `read-queries.ts` يستخدم بالفعل الفهارس الموجودة لتفاصيل
  الأوامر المختارة ومدة الإنتاج حسب الآلة، من كامل رولات وبنود كل أمر.
  لا يوجد مبرر من هذه التجربة لاستبدال ذلك بأرقام أول صفحة تاريخ.
- العدادات الدقيقة والمجموع الكامل للمخزون في `read.ts` تظل عمليات من كامل
  المصدر، ويمكن أن تنمو حتى لو أُصلح اختيار الأوامر. لا يُسمح بتقديرها من
  إحصاءات PostgreSQL أو عدّ قائمة العمل فقط.

## خطة التحسين للموافقة — لم تُنفذ

### 1. تجربة فهارس محلية محدودة

بعد الموافقة فقط، نقارن فهارس تغطية للرولات المنتهية وبنود الاستلام مع
الفهارس الموجودة `factory_rolls_order_stage` و`factory_receipt_items_order`.
الفكرة المرشحة: مفتاح أمر الإنتاج مع تضمين وزني الرول وشرط `stage='done'`،
ومفتاح أمر الإنتاج مع تضمين كمية الاستلام. هذه **ليست هجرة جاهزة للتنفيذ**.

يجب قياس الحجم على القرص، وكلفة الإدراج/الطباعة/التقطيع/الاستلام، وعمليات
جلب صفحات الجدول بعد كتابات حديثة، وليس أداء index-only بعد تحميل صناعي
ساكن فقط. عندما تكون أغلب الرولات منتهية يضم الفهرس الجزئي معظم الأرشيف،
وقد يخفض الكلفة لكنه لا يزيل ضرورة قراءته. لا نزعم رقماً لهذا البديل لأنه
لم يُنفذ. لا يُنقل أي فهرس إلى قاعدة التطبيق أو المنشورة دون تقرير وموافقة
منفصلين وخطة إنشاء آمنة وتراجع.

### 2. نموذج تجميع دقيق لتجنب إعادة قراءة الأرشيف

بعد موافقة مستقلة على إنشاء نموذج **في القاعدة المعزولة فقط**:

1. رصيد دقيق لكل أمر، بمقادير `NUMERIC` نفسها: جاهز الرولات، جاهز الأكياس،
   ومستلم. اختيار الأوامر ذات الرصيد الموجب من هذا المصدر، دون شرط حداثة،
   مع إبقاء اتحاد الأوامر النشطة والمخططة وصفوف الآلات كما هو.
2. تحديث الرصيد **داخل معاملة الكتابة نفسها** عند إنشاء رول جاهز، وإنهاء
   طباعة رول منتج رولات، والتقطيع، والاستلام. لا cache مؤقتاً ولا تحديثاً
   دورياً يمكن أن يسبق/يتأخر عن سجل المصدر. يجب أن يعالج الحذف المصرح
   والتصحيح والاستعادة أيضاً، وأن يتفق ترتيب الأقفال مع مسارات التنفيذ.
3. تبقى تفاصيل الأوامر المختارة ومدد الآلات في `read-queries.ts` مشتقة من
   كامل المصدر. لا حاجة لنسخ كل تفاصيل الأرشيف إلى جدول تجميعي.
4. لا يُخصم تسليم العميل من «المستلم في الصالة»: التسليم يخفض المخزون،
   وليس استلام التصنيع. وإذا احتجنا ملخصاً دقيقاً للإجماليات لاحقاً، يجب
   تحديث عدد السندات والحركات والرصيد بما فيها التسليم داخل المعاملة نفسها،
   لا اشتقاقها من الرصيد المتبقي في الصالة.
5. مراجعة جميع مسارات الكتابة، بما فيها
   `server/production/execution.ts` و`warehouse.ts` و`delivery.ts`
   و`server/order-production-delete.ts` ومسارات الاستعادة/الاستيراد، قبل
   اعتماد مصدر تجميعي. لا يكفي تحديث مسار واجهة واحد.
6. تعبئة أولية من المصدر الكامل مع بروتوكول يمنع فقد الكتابات المتزامنة:
   نافذة إيقاف كتابة معتمدة أو آلية catch-up موثقة ومختبرة. ثم مقارنة
   جميع الأوامر والإجماليات، وإعادة بناء قابلة للتحقق. لا نقترح تعبئة
   وتشغيلاً متزامنين بلا حماية.
7. إبقاء قراءات الحالة والملخصات داخل نفس
   `REPEATABLE READ READ ONLY`؛ اختبار تزامن الكاتب والقارئ وإعادة الطلب
   بعد فقد الاستجابة وعدم احتساب الزيادة مرتين.
8. بوابة قبول محلية مقترحة، وليست SLA: عند تثبيت العمل المفتوح وزيادة
   الأرشيف من 10 آلاف إلى 100 ألف ثم مليون، لا يحتوي مسار تحديد الرصيد
   الموجب على تجميع أو مسح خطي لأرشيف الرولات/الاستلامات؛ زمنه لا يزيد
   أكثر من 25% في عينات مكررة. تُقاس الإجماليات الدقيقة منفصلة والخدمة
   كاملة، ولا يُعلن ثبات زمن الفتح إذا بقيت الإجماليات تنمو خطياً.
   تُضاف توزيعات لاستلامات متعددة، عمل مفتوح كبير، وكتابات متزامنة.

هذه الخطة أوسع وأعلى مخاطرة من تبديل SQL؛ لا نزعم أنها مقاسة أو معتمدة.
موافقة النموذج المحلي ليست موافقة على تغيير القاعدة المنشورة. بعد إثباته،
يُعرض تصميم الهجرة والتكلفة وخطة rollback والإبقاء على القراءة الأصلية
للتراجع قبل أي تطبيق. النشر ليس تلقائياً.

## إعادة التشغيل والتحقق

```sh
mkdir -p generated-artifacts/hall-comparison
bash scripts/test-production-history-isolated.sh \
  --large --hall-comparison --hall-archive-size=10000 \
  > generated-artifacts/hall-comparison/10000.log 2>&1
bash scripts/test-production-history-isolated.sh \
  --large --hall-comparison --hall-archive-size=100000 \
  > generated-artifacts/hall-comparison/100000.log 2>&1
npm run check
npm test -- --runTestsByPath tests/production-hall-comparison.test.ts \
  tests/production-read-performance.test.ts tests/factory-production.test.ts --roots tests
```

الملفات المولدة مستثناة مسبقاً من Git والنشر. يرفض مشغل التجربة أعلام
المقارنة بدون `--local --large` قبل تشغيل الحالات، ويقصر الحجم على 10 آلاف
و100 ألف. يتحقق مساعد المقارنة من اسم القاعدة والمخطط وعنوان الحلقة
المحلية والمنفذ قبل استخدامه. لا يأخذ عنوان اتصال من سطر الأوامر.

نجح التشغيلان، بما فيهما:

- تطابق كامل لكل استجابة بين البدائل، وليس أرقام الأوامر فقط، مع تحقق
  الإجماليات من الجداول الأصلية والسبعين رصيداً قديماً وحالة 121 رولاً.
- **16** حالة اتساق لقطة: أربعة بدائل × شاشتين × حجمين. يلتزم كاتب محلي
  بتعديل استلام ومخزون بين استعلام الأوامر واستعلام الإجماليات؛ يظل القارئ
  يرى الاستجابة القديمة كاملة. تُستعاد الزيادة الصناعية بعد الحالة.
- **24** سيناريو PostgreSQL لدورة الإنتاج في كل تشغيل، بما فيها الاستلام
  الجزئي، التزامن، الصلاحيات، إعادة الطلب، والمقادير الدقيقة.
- فحص TypeScript و**33** اختبار وحدة في الملفات الثلاثة أعلاه.

لم تتغير واجهة المستخدم أو صلاحياتها. لا تدّعي هذه التجربة قياس زمن فتح
متصفح مسجل الدخول أو أداء الإنتاج الفعلي. بدأ خادم التطوير دون أخطاء بدء،
وعرضت المعاينة العامة شاشة تسجيل الدخول؛ لم تُفحص واجهة الصالة بحساب
مسجل الدخول.
